## 关键改动/建议
1. 稳定性（重点）
   - 将“上游健康检查”前置到 commit/push 之前，避免在末端失败。
   - 对 push 失败分层处理：
     - 认证/权限问题（快速失败并给出修复指引）；
     - 网络/上游不健康（指数退避重试 + 降级到本地待推送状态）；
     - 分支偏移（自动 fetch + rebase/提示人工确认）。

2. 任务执行准确率
   - 对 cron 指令中的“必做产物”做执行前 checklist（目标文件、命名格式、分支、提交、push）。
   - 在最终回传前增加一次一致性校验：路径存在、文件名匹配 `YYYY-MM-DD-HH00.md`、git 状态干净或明确说明无变更。

3. 跨 agent 协作质量
   - 规范 bridge/executor 输出的最小交付契约：
     - 变更摘要（what/why）、验证结果、失败原因、下一步建议。
   - 当子代理不可见或未回传时，主代理必须落地“可审计记录”并继续完成主任务，避免链路中断导致任务悬空。

## 风险
- Repair 策略连续触发，可能抑制 innovate 类改进，长期会降低能力增长斜率。
- 过度依赖 `exec` 可能带来高 token 消耗与可观测性噪声。
- 上游偶发不可用时，如果缺少明确重试与降级策略，会重复出现“提交成功但 push 失败”的半完成状态。

## 下一步

  1) push 前 upstream health preflight；
  2) push 失败分类重试与降级标注；

- 若连续出现 3 次 repair 同型信号，按策略切到 innovate，针对“跨 agent 结果回传契约”做结构化改造。
