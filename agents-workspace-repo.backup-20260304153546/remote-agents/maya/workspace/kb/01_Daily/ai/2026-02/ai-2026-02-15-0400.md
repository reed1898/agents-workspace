## HN AI 文章简报

### 1) [Show HN: Off Grid – Run AI text, image gen, vision offline on your phone](https://github.com/alichherawalla/off-grid-mobile)（[HN 讨论](https://news.ycombinator.com/item?id=47019133)）
- 摘要：这是一个“手机端离线 AI 全家桶”，把文本生成（GGUF/llama.cpp）、图片生成（本地 SD）、视觉问答（SmolVLM/Qwen3-VL 等）、语音转写（Whisper）和文档分析打包到同一 App 里，强调**零数据出端**。项目给出了较具体的性能范围（旗舰机文本 15–30 tok/s、图像 5–10s、视觉 ~7s），并提供架构/测试文档，明显在奔着“可长期维护”的工程化去做。
- 亮点：如果你在评估“端侧推理 + 隐私”产品线，这是一个可直接对标的开源参考实现（功能面比多数 local LLM app 更完整）。

### 2) [OpenAI sidesteps Nvidia with unusually fast coding model on plate-sized chips](https://arstechnica.com/ai/2026/02/openai-sidesteps-nvidia-with-unusually-fast-coding-model-on-plate-sized-chips/)（[HN 讨论](https://news.ycombinator.com/item?id=47016620)）
- 摘要：OpenAI 发布 GPT‑5.3‑Codex‑Spark，把推理部署在 Cerebras 芯片上，宣称**>1000 tokens/s**（约 15× 提速），定位为“速度优先”的 coding model（与更大更强的 full Codex 分层）。文中提到 Spark 为文本-only、128k 上下文，通过 Codex app/CLI/VS Code 扩展提供，并指出该速度提升的意义不止是体验，而是 OpenAI 在系统性降低对 Nvidia 的依赖。
- 亮点：**coding agent 的竞争维度从“更聪明”转向“更快 + 更便宜的迭代回路”**；做开发者工具/代理产品要开始按“延迟预算”设计。

### 3) [Two different tricks for fast LLM inference](https://www.seangoedecke.com/fast-llm-inference/)（[HN 讨论](https://news.ycombinator.com/item?id=47019691)）
- 摘要：文章对比了 Anthropic 与 OpenAI 的“fast mode”路径：一种更像是推理侧策略（降低 batch、用更贵的低延迟换吞吐），另一种是**上新更小/蒸馏模型 + 特殊硬件（Cerebras）**换极端速度。作者还提出一个非常产品化的观点：对 agent 工具而言，体验瓶颈往往不是纯速度，而是“错误率导致的返工成本”；**快但更容易犯错**不一定划算。
- 亮点：做 agent 产品时要把“速度提升”与“错误率/返工时间”一起量化，否则很容易买到“更快的烦恼”。

### 4) [Colored Petri Nets, LLMs, and distributed applications](https://blog.sao.dev/cpns-llms-distributed-apps/)（[HN 讨论](https://news.ycombinator.com/item?id=47018405)）
- 摘要：作者用 Colored Petri Nets（带数据 token 的 Petri 网）去承载并发/分布式协调，把很多手写并发控制（租约、限速、重试 backoff、pipeline backpressure 等）变成可形式化建模的“token 流动 + guard”。核心动机是：在 LLM 参与代码生成/修改时，**可验证正确性（编译器、类型、状态机/形式化约束）会极大放大 LLM 的实用性**。
- 亮点：一个可落地的思路是：把关键并发/资源协调逻辑“上升为可验证模型”，让 LLM 只在受约束的空间里生成/改动。

### 5) [Google says attackers used 100k+ prompts to try to clone AI chatbot Gemini](https://www.nbcnews.com/tech/security/google-gemini-hit-100000-prompts-cloning-attempt-rcna258657)（[HN 讨论](https://news.ycombinator.com/item?id=47019868)）
- 摘要：报道引用 Google 说 Gemini 遭遇“distillation / model extraction”攻击：通过大量、系统化的提示词探测（某次活动超过 10 万次），试图提取模型行为模式与“推理”相关机制，用于复制或增强竞争对手模型。Google 将其视为知识产权窃取，并警告这类攻击会扩散到更小公司和定制模型；一旦你的模型训练了敏感数据（例如交易策略），理论上也可能被“蒸馏式套取”。
- 亮点：如果你提供公网可交互的模型/代理服务，**“防蒸馏”将成为产品级安全需求**，不是研究话题。

### 7) [MathArena: Evaluating LLMs on uncontaminated math questions](https://matharena.ai/?view=problem&comp=aime--aime_2026)（[HN 讨论](https://news.ycombinator.com/item?id=47019304)）
- 摘要：MathArena 主打用“最新数学竞赛题”做评测，强调题目尽量避免训练污染，以检验模型真实泛化与推理能力。平台提供 leaderboard、成本估计，并说明用 item-response theory（IRT）来估计题目难度与模型能力；AIME 2026 的数据已上线。它把“推理能力”从单次答案对错，扩展到更系统、可统计的比较框架。
- 亮点：如果你在做模型选型/自研评测，MathArena 提供了一个“抗污染、可复现、带成本视角”的评估范式。

## 今日判断
1) **速度正在成为 coding agent 的核心差异化指标**：不仅是 UX，更会影响“迭代频率→产出”的乘数效应；但要警惕“快但错”带来的返工吞噬收益。
2) **模型抽取/蒸馏攻击会从头部蔓延到中小团队**：只要有公网交互接口，就会有人用系统化 query 套取行为规律；这对“私有知识/策略”类模型风险更高。
3) **“可验证约束”会成为 LLM 参与复杂系统的关键放大器**：形式化模型/状态机/类型与测试，让 LLM 更敢用、也更可控。

## 建议行动
1) 给你的 agent/开发者工具补一套指标：把“端到端完成时间”拆成 **生成时间 + 工具调用时间 + 人工返工时间**；用同一任务跑不同模型/模式，算出真实 ROI。
2) 若你有公网 API/产品：做一版“防蒸馏”最小实现（速率限制 + 异常查询模式检测 + 分层输出/水印/策略），并把它纳入安全审计清单。
3) 选一个高价值流程（例如：文档结构化、代码修改 PR 流水线、或爬虫调度）做 1 周 PoC：用“受约束的状态机/CPN/可验证框架 + LLM”组合，验证 bug 率与交付速度是否能显著改善。
